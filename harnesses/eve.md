# Eve (Vercel)

> eve is Vercel's TypeScript framework for durable backend agents, released June 2026. An agent is a directory (`agent/instructions.md`, `agent/tools/*.ts`, `agent/skills/`, `agent/channels/`, `agent/schedules/`, `agent/subagents/`, …). A build step discovers that directory and compiles it into a Nitro server. That server runs every session as one long-lived Workflow SDK run and every model step as a durable `"use step"`. Each single model call is delegated to the Vercel AI SDK 7 `ToolLoopAgent`, capped at one step. eve owns everything around that call: the turn and session loops, human-in-the-loop parking, tasks and subagents, compaction, sandboxes, channels, tracing and evals. It sits firmly at the **agent-framework** layer. It combines durable execution with server deployment, channels, sandboxes, approvals and client surfaces. Build on it if you want long-running, multi-channel, approval-gated backend agents with crash-safe execution and you accept a server-shaped (not in-process) programming model. The model is portable in principle but smoothest on Vercel. Don't pick it if you want a small library to embed a loop in your own process.

## 1. Layering & package map

The monorepo has one published package, `eve`. It contains the framework, the CLI/TUI and all first-party extensions. A ring of private workspace packages gets *vendored into* `eve` at build time. AGENTS.md states the policy: keep `nitro` as the only runtime dependency and vendor everything else ([`AGENTS.md:L128-L135`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/AGENTS.md#L128-L135)). The manifest matches: runtime `dependencies` are only `nitro@3.0.260903-beta` and `undici` ([`packages/eve/package.json:L578-L580`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/package.json#L578-L580)). `ai` (^7.0.137), `just-bash`, `microsandbox`, `chat`, `braintrust` and `dd-trace` are (mostly optional) peers ([`packages/eve/package.json:L660-L668`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/package.json#L660-L668)). The AI SDK providers, `@ai-sdk/mcp`, `@ai-sdk/code-mode`, `@workflow/*`, `@vercel/sandbox`, the ACP SDK, the MCP server SDK and OpenTelemetry are bundled by `scripts/vendor-compiled` into `#compiled/*` ([`packages/eve/scripts/vendor-compiled/index.mjs:L6-L64`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/scripts/vendor-compiled/index.mjs#L6-L64)).

## 2. Agent loop

The loop is three nested loops, each with a different durability boundary.

**(a) Session loop (workflow body).** `workflowEntry` is the single `"use workflow"` entry point for root and delegated sessions ([`packages/eve/src/execution/session/entry.ts:L58-L68`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/entry.ts#L58-L68)). Boot claims the stable session hook and optional channel continuation alias in parallel with `createSessionStep` ([`entry.ts:L95-L133`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/entry.ts#L95-L133)). `runPreparedSession` then builds a `SessionStateCursor` and a `SessionHandoff` ([`packages/eve/src/execution/session/program.ts:L97-L160`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/program.ts#L97-L160)). `runSessionLoop` alternates between running a turn and parking on the inbox (`nextParkedActivity`). It handles `expired | reset | closed | clear | compact | cancel-turn | turn` commands and tries a compaction handoff whenever the session is idle ([`program.ts:L211-L409`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/program.ts#L211-L409)). While parked, the run holds no compute.

**(b) Turn loop (workflow body).** `SessionExecution.runTurnSteps` repeatedly calls `turnStep` through `cursor.advanceWithHistory`. It then branches on the step result ([`packages/eve/src/execution/session/turn.ts:L167-L262`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn.ts#L167-L262)):
- `done` → turn completes.
- `held/request` → wait for an approval answer, sign-in callback, or steering message from the *same principal* ([`turn.ts:L364-L385`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn.ts#L364-L385)). A session without the `requestInput` capability (e.g. a markdown schedule) throws instead ([`turn.ts:L217-L224`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn.ts#L217-L224)).
- `held` (tasks) → the model tried to end the turn while background tasks work, so the turn parks as if `eve__task_wait` were called ([`turn.ts:L331-L353`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn.ts#L331-L353)).
- `park` with pending coordination call IDs → dispatch workflow-tool runs, then wait for runtime results, task waits (durable `sleep` timers, [`turn.ts:L589-L602`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn.ts#L589-L602)), steering and cancellation ([`turn.ts:L387-L470`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn.ts#L387-L470)).
- otherwise → next step, carrying any steering delivery.

**(c) Step (durable step).** `turnStep` is the `"use step"` boundary ([`packages/eve/src/execution/session/turn-step.ts:L105-L114`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn-step.ts#L105-L114)). Inside it, eve deserializes the ALS context, matches sign-in callbacks, and runs the channel adapter's `deliver` hook per payload. It refreshes dynamic tools and subagents when the deployment revision changed ([`turn-step.ts:L415-L466`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn-step.ts#L415-L466)). It then calls `runModelCallBatch` with `experimental.workflow.modelCallsPerStep` (default 1) ([`turn-step.ts:L468-L563`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/turn-step.ts#L468-L563)). Batching keeps calling the harness until it needs coordination, authorization or input ([`packages/eve/src/execution/model-call-batching.ts:L5-L65`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/model-call-batching.ts#L5-L65)).

**Harness step.** `createExecutionNodeStep` wires the resolved node's tools, model resolver and dynamic-model dispatcher into `createToolLoopHarness` ([`packages/eve/src/execution/node-step.ts:L89-L133`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/node-step.ts#L89-L133)). One harness step runs in this order ([`packages/eve/src/harness/tool-loop.ts:L75-L154`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/tool-loop.ts#L75-L154)):
1. `settleRuntimeWork` (results from parked runs).
2. `acceptHumanInput` (approval answers and queued input).
3. `prepareTurnInput`, then `openTurn` (memory recall and dynamic instructions are prepended).
4. `admitApprovedWork`.
5. `runModelStep`.

`runModelStep` builds the prompt, selects the model (possibly via a dynamic-model resolver) and dispatches approved workflow calls. It enforces the session budget, runs approved *local* calls, builds the step's tool catalog, and invokes `ModelCaller` ([`packages/eve/src/harness/model-call/run.ts:L63-L178`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/run.ts#L63-L178)).

**The AI SDK sits at the bottom of the loop.** Each attempt constructs a fresh `ToolLoopAgent` with `stopWhen: isStepCount(1)`, eve's `prepareStep/onStepStart/onStepEnd` hooks, a `toolApproval` callback, `reasoning`, and a 10-minute chunk/first-chunk timeout ([`packages/eve/src/harness/model-call/call.ts:L347-L393`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/call.ts#L347-L393); timeout constant at [`call.ts:L78-L83`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/call.ts#L78-L83)). The stream is published as protocol events while it arrives (`emitStreamContent`) ([`call.ts:L416-L497`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/call.ts#L416-L497)). Tools with an `execute` run *inside* the AI SDK call. Concurrent execution of multiple calls in one step is AI SDK behavior, which eve inherits (inference from the SDK's semantics; eve adds no serialization). Workflow tools, subagent tools and task tools are surfaced without `execute` (client-side tools). After the response, `handleStepResult` collects them with `collectWorkflowCalls` and parks on them or on approvals ([`packages/eve/src/harness/step/after-model.ts:L77-L170`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/step/after-model.ts#L77-L170)). eve uses the AI SDK as a single-step executor and owns the multi-step loop itself. This is the same split the AI SDK chapter describes for `ToolLoopAgent`, with eve's durable boundary inserted between steps.

**Stop conditions.** A turn ends when the model returns no further calls or when every call in the step has `endsTurn` and succeeds ([`packages/eve/src/tools/definition.ts:L270-L288`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/tools/definition.ts#L270-L288)). Other stops: structured `outputSchema` output, a session usage limit (`enforceBudget` asks "continue?" or fails, [`packages/eve/src/harness/hitl/index.ts:L114-L130`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/hitl/index.ts#L114-L130)), cancellation, or failure. I found no explicit max-steps-per-turn knob. Bounding is by token/cost limits (`SessionRuntimeUsageLimits` with `inputTokens`, `outputTokens`, `costUsd`; [`packages/eve/src/harness/session-usage-limits.ts:L1-L40`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/session-usage-limits.ts#L1-L40)) and the session timeout (30 days by default).

**Steering and queued messages.** Deliveries default to `turnPolicy: "steer"`. Only the turn's own principal can steer; other principals' messages queue ([`packages/eve/src/execution/session/input-queue.ts:L238-L254`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/input-queue.ts#L238-L254)). `GenerationSteering` aborts in-flight generation only if no assistant output has streamed and no tool effect has started. After that point, steering applies at the next committed boundary ([`packages/eve/src/harness/generation-steering.ts:L10-L87`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/generation-steering.ts#L10-L87)). A steered call returns `{ next: runStep, steered: true }` and keeps the interrupted call's usage ([`call.ts:L196-L216`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/call.ts#L196-L216)). `turnPolicy: "queue"` holds messages until the turn settles (docs: [`execution-model-and-durability.mdx:L235-L270`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/execution-model-and-durability.mdx#L235-L270)).

**Retries and recovery.** Transient model errors get 3 attempts with 500 ms exponential backoff plus jitter ([`packages/eve/src/harness/model-call/retry.ts:L14-L63`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/retry.ts#L14-L63)). Each attempt rebuilds tools, request and agent, and settles calls the discarded attempt had announced ([`call.ts:L151-L189`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/call.ts#L151-L189)). Two one-shot recoveries follow ([`packages/eve/src/harness/model-call/recovery.ts:L20-L36`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/recovery.ts#L20-L36)):
- If a gateway fallback provider rejects a provider tool (e.g. native web search), eve drops that tool and adds a system note.
- An empty response is reissued with a nudge.

Anything left over falls back to Workflow's durable step retry from the last committed snapshot.

## 3. Model / provider abstraction

eve has no provider layer of its own. Its message model is AI SDK `ModelMessage`, refined so that every user-role message carries a `kind`: `user`, or a framework kind such as `context.instruction`, `context.state`, `context.compaction`, `memory.load`, `execution.continuation`, `execution.retry` or `task.result` ([`packages/eve/src/harness/messages.ts:L14-L36`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/messages.ts#L14-L36)). Compaction and projection use this classification to tell human text from framework scaffolding.

**Model resolution.** `resolveRuntimeModelReference` checks bootstrap models, then mock models (evals), then source-backed `LanguageModel` objects from `agent.ts`. Otherwise it returns the bare string id, which the AI SDK resolves through the **Vercel AI Gateway** ([`packages/eve/src/runtime/agent/resolve-model.ts:L54-L77`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/runtime/agent/resolve-model.ts#L54-L77)). The scaffold default is a Gateway id (`openai/gpt-6-luna-fast`). eve ships direct helpers built on vendored `@ai-sdk/anthropic` / `@ai-sdk/openai` ([`packages/eve/src/public/models/anthropic/index.ts:L1-L13`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/public/models/anthropic/index.ts#L1-L13)) and a `chatgpt()` model billed to a local ChatGPT subscription. That model spawns `codex app-server --stdio` to borrow Codex's login and works only in local dev ([`packages/eve/src/public/models/openai/index.ts:L7-L31`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/public/models/openai/index.ts#L7-L31), [`.../chatgpt/codex-app-server.ts:L181`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/public/models/openai/chatgpt/codex-app-server.ts#L181)). This is a direct cross-reference to the Codex chapter's app-server protocol. Any AI SDK provider package can be passed as a `LanguageModel`. `eve/models` also exports `auto()`, which routes per step among configured models via an AI SDK `Experimental_DecisionModel` ([`packages/eve/src/models/auto.ts:L1-L60`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/models/auto.ts#L1-L60)).

**Provider quirks** are centralized in a `ModelProfile`. Fields: `gateway`, `provider` (the host, not the family), `anthropicCache` (TTL), `filesOutsideToolResults` (Chat Completions APIs), and `googleSearchDropsTools` (pre-Gemini-3) ([`packages/eve/src/harness/model-profile.ts:L12-L67`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-profile.ts#L12-L67)).

**Prompt caching.** Gateway routes cache automatically. For Anthropic hosts, eve stamps both `anthropic.cacheControl` and `bedrock.cachePoint` breakpoints with one uniform TTL ([`packages/eve/src/harness/prompt-cache.ts:L9-L30`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/prompt-cache.ts#L9-L30)). Several choices are explicitly cache-preserving: retry notes go in a trailing user message rather than the system prompt ([`call.ts:L333-L335`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/call.ts#L333-L335)), and the deferred-tool catalog is announced append-only (§4).

**Reasoning** is passed as the AI SDK `reasoning` setting from the agent/model reference ([`call.ts:L381`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/call.ts#L381)). Reasoning deltas are streamed as `reasoning.appended` events.

**Token and cost accounting.** `extractTokenUsageDelta` records input, output, cache-read and cache-write tokens. Cost comes from Gateway provider metadata (`providerMetadata.gateway.cost`), so **dollar cost is only known when routed through AI Gateway** ([`packages/eve/src/harness/model-call/usage.ts:L20-L58`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/usage.ts#L20-L58)). Running totals are written to workflow-run attributes (`$eve.input_tokens`, `$eve.cost_usd`, …) for the dashboard ([`usage.ts:L60-L89`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/usage.ts#L60-L89)). Context-window sizes come from the Gateway model catalog (`/v1/models/catalog`) at compile time ([`packages/eve/src/compiler/model-catalog.ts:L1-L16`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/compiler/model-catalog.ts#L1-L16)). Non-catalog models must supply `modelContextWindowTokens` (CHANGELOG 0.77.0).

## 4. Tool system

**Definition API.** `defineTool({ description, inputSchema, outputSchema?, execute, approval?, approvalKey?, endsTurn?, toModelOutput?, label?, deferred?, availableInSubagents? })`. `inputSchema` accepts Standard Schema (Zod etc.), Standard JSON Schema or raw JSON Schema ([`packages/eve/src/tools/definition.ts:L78-L104`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/tools/definition.ts#L78-L104), [`L258-L330`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/tools/definition.ts#L258-L330)). There is no `name` field: the tool's name is the filename slug, validated against `^[a-zA-Z][a-zA-Z0-9_-]{0,63}$` ([`packages/eve/src/discover/grammar.ts:L114-L127`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/discover/grammar.ts#L114-L127)). `execute(input, ctx)` receives a `ToolContext` with these members ([`definition.ts:L182-L228`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/tools/definition.ts#L182-L228)):
- session metadata
- `abortSignal`, `callId`, `toolName`
- `messages` (the model input of the requesting step)
- `getToken(provider)` / `requireAuth(provider)` for inline OAuth
- `getSandbox()`
- `approval.responder` (who approved)

Execute may return a value, a promise, or an `AsyncIterable` for streamed progress.

**Durable tools.** `defineWorkflowTool` requires `"use workflow"` as the executor's first statement. Each call is its own Workflow run, with `ctx.ask` (human question) and `ctx.agent` (subagent). It has three entry points: `execute` (blocks the turn), `task` (returns a receipt and runs in the background), and `serve` (resumable task) ([`research/tools-as-workflows.md:L8-L80`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/research/tools-as-workflows.md#L8-L80)). In the harness, workflow-handled tools become `createWorkflowToolHarnessDefinition` entries ([`packages/eve/src/execution/node-step.ts:L214-L250`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/node-step.ts#L214-L250)).

**Execution pipeline.** `buildToolSet` converts each `HarnessToolDefinition` into an AI SDK `tool()` with `strict: false`. It wraps `execute` for tool stubs (evals) and for out-of-band `AuthorizationSignal` stashing, so OAuth URLs never enter model history ([`packages/eve/src/harness/tools.ts:L37-L140`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/tools.ts#L37-L140)). `toModelOutput` lets a tool project a different model-facing result while channels still see the full output.

**Built-in tools.** Defaults occupy the same `agent/tools/<name>.ts` slots as authored tools, so a file at the same path replaces the default and `disableTool()` removes it ([`docs/concepts/built-in-tools.md:L8-L27`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/built-in-tools.md#L8-L27)).

| Tool | Default? | Notes |
|---|---|---|
| `bash` | yes | Runs in the sandbox. Yields after 30 s, leaving the command running as a process group with output in `/tmp/.eve/jobs/<id>` ([`execution/sandbox/bash.ts:L10-L13`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/sandbox/bash.ts#L10-L13)) |
| `read_file` / `write_file` | yes | Line-numbered reads. Images ≤3 MiB / PDFs ≤20 MiB go to the model as files. Read-before-write and stale-read checks |
| `web_fetch`, `web_search` | yes | `web_search` prefers a provider-native tool and drops it on gateway fallback |
| `agent` | yes (root-only) | Delegates to a fresh copy of the root agent as a task |
| `eve__search`, `eve__tool`, `eve__skill` | auto | Catalog for deferred tools, connection tools and skills |
| `eve__task_wait`, `eve__task_cancel` | auto | Present when any task-producing tool exists |
| `glob`, `grep`, `ask_question`, `no_reply`, `sleep`, `workflow`, `agentRouter()` | opt-in | `workflow` = model-written JS orchestrating ≤128 agents (§9) |

**Output truncation.** Framework tools cap output at the source: 2,000 lines, 50 KiB, and 2,000 chars per line, keeping the head by default ([`packages/eve/src/execution/sandbox/truncate-output.ts:L1-L25`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/sandbox/truncate-output.ts#L1-L25)). Authored tools are expected to bound their own output. Compaction caps oversized historical results later (§5).

**Deferred tools and catalog.** Tools marked `deferred: true`, every connection (MCP/OpenAPI) tool, and deferred skills stay out of the tool list. The model reaches them through `eve__search` (tiered ranking: exact name, suffix after `__`, connection name, prefix, keyword) and calls them via `eve__tool`. Availability is announced in an append-only context message that names namespaces but never deferred entries, so the cached prefix stays stable ([`docs/concepts/built-in-tools.md:L302-L324`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/built-in-tools.md#L302-L324); catalog built per step in [`packages/eve/src/execution/catalog/step-catalog.ts:L136`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/catalog/step-catalog.ts#L136)). The design is the same "tool search" pattern seen in Claude Code and Deep Agents, but here it covers MCP servers and skills uniformly.

**Approvals** are policies, not modes. `approval` is either a request policy `(ctx) => ApprovalStatus` (`"approved" | "denied" | "user-approval" | "not-applicable"`, optionally with a reason) or `{ request, response?, prompt? }`. The `response` policy decides whether *this* authenticated responder may approve this request ([`packages/eve/src/approval/definition.ts:L64-L164`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/approval/definition.ts#L64-L164)). Helpers ([`packages/eve/src/tools/approval/policies.ts:L86-L131`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/tools/approval/policies.ts#L86-L131)):
- `always()`
- `never()`
- `once()`, which records approved tool names per session
- `auto()`, an LLM classifier

`auto()` sends the exact tool name and input (≤64 KiB, no conversation history) to a decision model, by default `typesafe-ai/jev`, under a 30 s timeout. It fails closed to `user-approval` ([`policies.ts:L26-L64`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/tools/approval/policies.ts#L26-L64)). Policies plug into the AI SDK's `toolApproval` hook ([`packages/eve/src/harness/tools.ts:L208-L224`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/tools.ts#L208-L224)). Approved calls are re-checked just before execution (`recheckApprovedCall`, [`tools.ts:L226-L245`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/tools.ts#L226-L245)). eve strips the SDK's approval parts and parks the step itself (`parkOnApprovals`, [`packages/eve/src/harness/hitl/index.ts:L56-L70`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/hitl/index.ts#L56-L70); comment at [`after-model.ts:L108`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/step/after-model.ts#L108)). A `SuspendedStep` withholds the assistant response from history until every call in it has a result ([`packages/eve/src/harness/session-machine/state.ts:L22-L43`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/session-machine/state.ts#L22-L43)).

## 5. Context management

**System prompt assembly.** `agent/instructions.md` (or `.ts`, or an `instructions/` directory of `.md`/`.ts` files; legacy `system.md` with a warning) is the always-on system prompt ([`packages/eve/src/discover/grammar.ts:L193-L200`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/discover/grammar.ts#L193-L200)). Per call, `modelInstructions` concatenates `[retry note] + agent.system + step system messages`. The step system messages are dynamic system-role instructions plus the `[Tasks]` note, and an Anthropic cache breakpoint is applied ([`packages/eve/src/harness/model-call/request.ts:L27-L82`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/request.ts#L27-L82)). Skill names and descriptions, deferred-catalog announcements and pending-approval notes enter as classified user-role framework messages. Dynamic instructions (`defineDynamic` on `session.started`/`turn.started`) can be system-role (re-resolved per deployment) or user-role (pinned in durable history once) ([`packages/eve/src/dynamic/definition.ts:L13-L40`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/dynamic/definition.ts#L13-L40)).

**Project instruction files.** The runtime agent does **not** read `AGENTS.md`/`CLAUDE.md`. Its prompt is `instructions.md`. `eve init` *generates* `AGENTS.md` and a `CLAUDE.md` containing `@AGENTS.md` for the coding agents that author the project ([`packages/eve/src/setup/scaffold/create/project.ts:L299`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/setup/scaffold/create/project.ts#L299)), and the published package bundles its docs under `node_modules/eve/docs`. eve is built to be written by coding agents, not to be one.

**Compaction.**
- Trigger: before each attempt, `shouldCompact` compares the last provider-reported input-token count plus a character estimate of newer messages plus the fixed compaction-prompt envelope against `threshold = floor(contextWindow × thresholdPercent)`. The defaults are 0.9 and a recent window of 10 messages ([`packages/eve/src/harness/compaction/engine.ts:L31-L79`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/compaction/engine.ts#L31-L79); defaults at [`packages/eve/src/execution/session.ts:L12-L48`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session.ts#L12-L48)).
- Algorithm (`compactMessages`, [`engine.ts:L176-L259`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/compaction/engine.ts#L176-L259)):
  1. Run heuristics first (currently `toolResultCapHeuristic`, which caps old tool results in place and annotates them "Re-run the tool if you need the full output").
  2. If still over the threshold, split into older and recent messages and summarize the older part with a checkpoint prompt, passing the previous checkpoint separately.
  3. Emit `[marker user msg, summary assistant msg, …recent]`.
  4. Degrade in order: verbatim recent tail, then recent tail with tool results stripped, then a smaller window.
- Model: compaction uses the turn model unless `compactionModelReference` is set.
- Triggers and events: compaction can be forced by clients (`ClientSession.compact()`, `POST …/compact`) and emits `compaction.requested`/`compaction.completed`.
- Memory: memory providers capture before compaction and recall after it.
- Run reset: after compaction, the idle session is **moved to a fresh workflow run** to bound event-log growth (§6) ([`docs/concepts/default-harness.md:L8-L39`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/default-harness.md#L8-L39)).

**Spill-to-disk.** There is no automatic spill of large tool results to files. Large outputs are truncated at the source. Attachments are staged into the sandbox and referenced as `eve-sandbox:` refs that are hydrated only for the outgoing call, so history keeps refs rather than bytes ([`call.ts:L318-L322`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/harness/model-call/call.ts#L318-L322)). Long-running `bash` output lives in `/tmp/.eve/jobs/` files.

**Memory.** `agent/memory/<slot>.ts` uses `defineMemory({ description, provider, scope })`. eve drives the provider through `recall` at `turn.started`, its tools, capture at `turn.completed`, and pre/post-compaction hooks. Providers are the built-in file provider (local or Vercel Blob backend), Supermemory and Upstash ([`docs/memory/overview.mdx:L1-L50`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/memory/overview.mdx#L1-L50); lifecycle in [`packages/eve/src/context/memory-lifecycle.ts:L45-L321`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/context/memory-lifecycle.ts#L45-L321)). Session-scoped durable state is `defineState(name, initial)` ([`packages/eve/src/public/definitions/state.ts:L43`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/public/definitions/state.ts#L43)).

## 6. State, sessions & durability

**Storage.** A session is a Workflow run. Its id is the run id (`wrun_…`), and its public event stream is the run's writable stream (NDJSON at `GET /eve/v1/session/:id/stream`). Durable state is whatever the configured **Workflow World** persists:
- `@workflow/world-local` writes under `.eve/.workflow-data` by default (dev and `eve start`).
- `@workflow/world-vercel` is used on Vercel.
- Any package named in `experimental.workflow.world` (e.g. `@workflow/world-postgres`, which CI exercises via the `e2e/matrix.json` `worlds` entry) is the third option ([`docs/concepts/execution-model-and-durability.mdx:L16-L24`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/execution-model-and-durability.mdx#L16-L24), [`L167-L184`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/execution-model-and-durability.mdx#L167-L184)).

eve validates and wraps the world (adding a stranded-replay guard) before starting it ([`packages/eve/src/execution/install-workflow-world.ts:L13-L19`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/install-workflow-world.ts#L13-L19)). Every run is started on an *exact* deployment id and stamped with the eve version ([`packages/eve/src/execution/workflow-runtime.ts:L575-L605`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/workflow-runtime.ts#L575-L605)).

**Replay economics.** Workflow replay re-reads every step's *output*. eve's step outputs therefore return only a **delta** of `{serializedContext, sessionState, history}` against the step's input, and the workflow body applies it. Neither replay nor storage carries the whole session once per step ([`packages/eve/src/execution/session/state-delta.ts:L35-L78`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/state-delta.ts#L35-L78)).

**Crash recovery semantics.** Completed steps are never re-run; their recorded results replay. An interrupted step re-runs *including its inline tool executions*. Non-idempotent tools therefore need downstream idempotency or reconciliation; an approval gate controls authorization but does not close the crash window after an approved effect. Stream consumers may see both attempts' events under new ids ([`execution-model-and-durability.mdx:L202-L217`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/execution-model-and-durability.mdx#L202-L217)). With `modelCallsPerStep > 1`, the whole batch is one replay unit. Approvals, input requests and blocking coordination always force a checkpoint before waiting ([`model-call-batching.ts:L43-L65`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/model-call-batching.ts#L43-L65)). Parked work (approval, OAuth sign-in, task wait, workflow-tool body waiting on a hook/timer) holds no compute.

**Deployment handoff.** An eve session can outlive deployments, and few harnesses in this study handle that. One owner run executes all turns. When a delivery accepted by a *different* deployment reaches an *idle* session, `SessionHandoff.tryTransfer` checkpoints the session (`SESSION_CHECKPOINT_VERSION = 15`) and starts a successor run on that exact deployment. The original run stays parked as the stream anchor ([`packages/eve/src/execution/session/handoff.ts:L99-L175`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/handoff.ts#L99-L175)). Successors upgrade checkpoints from version ≥8 (eve 0.66.0) ([`packages/eve/src/execution/session/checkpoint-migrations.ts:L8-L12`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/checkpoint-migrations.ts#L8-L12)). The same mechanism powers the post-compaction move to a fresh run on the same deployment ([`program.ts:L280-L290`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session/program.ts#L280-L290)). The design rationale is in [`research/single-workflow-session-upgrades.md`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/research/single-workflow-session-upgrades.md). It replaced a driver plus child-turn-run topology that the turn-performance study measured at ~3.1 s fixed overhead per sequential hosted turn ([`research/turn-performance.md:L9-L48`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/research/turn-performance.md#L9-L48)).

**Stranded sessions.** A run can only be replayed by the eve version that started it. On worlds other than Vercel's (no per-deployment routing), every eve upgrade **strands** existing sessions. Root sessions are reset on their next channel message, with the replacement receiving `ctx.session.predecessor`. Child runs are cancelled ([`execution-model-and-durability.mdx:L40-L73`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/execution-model-and-durability.mdx#L40-L73); guard at [`packages/eve/src/execution/session-inbox/stranded-replay-guard.ts:L36`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/session-inbox/stranded-replay-guard.ts#L36)). This is the concrete portability cost of durable execution off Vercel.

**Resume/fork/undo.** Sessions resume by id or by channel continuation address. `clear` (drop model history but keep identity, state and sandbox), `compact` and `reset` are first-class operations. I found **no fork/branch or undo/rewind** primitive, which matches eve's backend-agent focus rather than an interactive coding-agent one.

## 7. Safety & sandboxing

**Two trust zones.** The app runtime runs the loop, tools, connections, secrets and durable state with full Node access. The sandbox runs only shell commands and file operations from the built-in `bash`/`read_file`/`write_file`/`glob`/`grep`, which *proxy* into it. Secrets never enter the sandbox ([`docs/concepts/security-model.md:L8-L22`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/security-model.md#L8-L22)). The corollary: **authored tool code is not sandboxed** and runs with the deployment's privileges.

**Sandbox providers.** Providers implement `SandboxProviderImplementation { prepare, start, resume, onSessionEnd }` ([`packages/eve/src/shared/sandbox-provider.ts:L131-L158`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/shared/sandbox-provider.ts#L131-L158)). `ensureSandboxAccess` checkpoints provider state so later steps and restarts call `resume()` rather than re-running the selector ([`packages/eve/src/execution/sandbox/ensure.ts:L64-L150`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/sandbox/ensure.ts#L64-L150)). Built-ins:
- Vercel Sandbox (Firecracker microVM on Vercel; credentials from Vercel OIDC, [`.../bindings/vercel-credentials.ts:L11-L35`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/sandbox/bindings/vercel-credentials.ts#L11-L35))
- Docker
- microsandbox (microVM)
- just-bash (a JavaScript bash emulator with a virtual FS, i.e. **no OS isolation**)

`DefaultSandbox` picks Vercel on Vercel, otherwise Docker → microsandbox → just-bash by availability ([`docs/sandbox/default.mdx:L1-L17`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/sandbox/default.mdx#L1-L17)). A host with no Docker or microVM support silently gets the weakest isolation.

**Network policy.** `SandboxNetworkPolicy` is literally an alias of Vercel Sandbox's `NetworkPolicy` (`allow-all`, `deny-all`, domain allow-lists, per-domain header `transform` for credential brokering, `forwardURL`) ([`packages/eve/src/shared/sandbox-network-policy.ts:L1-L33`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/shared/sandbox-network-policy.ts#L1-L33)). Docker honors only `allow-all`/`deny-all` and throws on anything finer ([`.../bindings/docker-network.ts:L10-L21`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/execution/sandbox/bindings/docker-network.ts#L10-L21)). Domain allow-lists and firewall credential brokering therefore need Vercel Sandbox or microsandbox.

**Approvals and identity.** See §4 for request and response policies, `auto()`, and re-check before dispatch. Approval prompts from descendants are relayed to the root channel. A notable fix in 0.78.0: approved calls now always run *as the requester*, not the approver, closing a privilege escalation (`packages/eve/CHANGELOG.md`, 0.78.0 entry `9559de8`). Session budgets (`inputTokens`, `outputTokens`, `costUsd`) can pause a turn on a "continue?" request.

**Ingress auth fails closed.** Routes reject unauthenticated traffic unless `none()` is explicit, and the scaffold's `placeholderAuth()` stays closed in production ([`packages/eve/src/public/channels/auth.ts:L788-L817`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/public/channels/auth.ts#L788-L817); helpers `vercelOidc`, `httpBasic`, `oidc` at L1116-L1240). Platform channels verify HMAC signatures in constant time. Markdown frontmatter `---js` engines are disabled ([`security-model.md:L76-L82`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/security-model.md#L76-L82)). Connection tokens are cached per step and never serialized to durable state.

## 8. Extensibility

**Every capability is a file slot**, and framework defaults are ordinary sources at canonical logical paths. ## 9. Multi-agent

eve's multi-agent model is **task-centric and durable**.

- **Kinds of subagent** ([`docs/subagents/index.mdx:L6-L60`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/subagents/index.mdx#L6-L60)):
  - The root-only built-in `agent` tool: a copy of the root that shares tools, connections and sandbox, with fresh history and state.
  - Declared subagents under `agent/subagents/<id>/`: their own agent root that inherits *nothing*, with their own sandbox and their own nested subagents.
  - Remote agents (`defineRemoteAgent`, `defineWorkspaceAgent`): separately deployed eve agents called over authenticated HTTP.
- **Uniform model-facing shape.** All three lower to a tool `{ message, taskId? }`. Every call returns a task receipt immediately, the child runs as its own durable session, and its final reply arrives later as a `task.result` message. `eve__task_wait` / `eve__task_cancel` manage waiting, and a `[Tasks]` note lists working and idle tasks. Children *park* after answering and are continued by `taskId`. Sending to a working child joins its current turn as steering ([`docs/subagents/index.mdx:L211-L250`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/subagents/index.mdx#L211-L250); child run input built in [`packages/eve/src/subagents/tool.ts:L57`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/subagents/tool.ts#L57)).
- **Ownership split.** The design note sets one rule for who owns what: task runs own readiness, progress, input obligations and cancellation; the subagent executor owns handles and transport; the harness owns model history and approvals ([`research/executor-neutral-core.md:L81-L105`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/research/executor-neutral-core.md#L81-L105)).
- **Human-in-the-loop crosses boundaries.** Descendant `input.requested`/`authorization.required` events are proxied to the root channel, and answers are routed back down. An approval stays open on the parent until the descendant, whose response policy decides, settles it.
- **Parallelism.** Several children can run at once. The 0.78.0 changelog says a step that starts several workflow-tool runs starts them in parallel. The opt-in **`workflow` tool** lets the model write a JavaScript function body that calls `ctx.agent(name, { message, outputSchema? })`. It runs in `@ai-sdk/code-mode`'s isolated runtime with interrupts bridged to durable agent calls, capped at 128 agents per program (default 100) ([`packages/eve/src/tools/provided/workflow.ts:L11-L56`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/tools/provided/workflow.ts#L11-L56); [`packages/eve/src/shared/workflow-sandbox.ts:L1-L41`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/shared/workflow-sandbox.ts#L1-L41)). This is a "code mode" orchestrator over durable subagents. Authored workflow tools can do the same deterministically with `ctx.agent()` and `ctx.ask()`.
- **Isolation.** There are no git worktrees. Isolation comes from per-subagent sandboxes, while root copies share one sandbox ("give parallel children non-overlapping write scopes"). There is no depth limit beyond the authored tree; the built-in `agent` cannot recurse. There are no OpenAI-style *handoffs* (transfer of conversation control): subagents always return to the caller.

## 12. Notable design decisions & trade-offs

1. **The AI SDK runs one step; eve runs everything else.** Pinning `ToolLoopAgent` to `isStepCount(1)` puts a durable checkpoint between every model call. The AI SDK supplies provider normalization, streaming, tool-call parsing and inline tool execution. eve rebuilds the agent per attempt so stale one-shot hooks cannot leak across retries. The cost is a hard dependency on fast-moving AI SDK 7 APIs (CHANGELOG 0.77.0: "eve now requires `ai` 7.0.137 or later"). Another cost is that inline tool side-effects sit inside the replay unit.
2. **Durable by default, priced in latency.** Every step is a persisted Workflow step, and step outputs are diffs to keep replay cheap. eve's own research measured multi-second fixed per-turn overhead on hosted Workflow and rewrote the topology into single-workflow sessions with deployment handoff to cut it. The opt-in `modelCallsPerStep` exists to trade checkpoint granularity for speed.
3. **Long-lived sessions vs. code upgrades.** Sessions are meant to live for weeks (30-day default timeout) across deployments. Supporting that took checkpoint versioning, idle-only handoff, compaction handoff and "stranded session" semantics. Off Vercel, upgrading eve means existing sessions reset on their next message. That is a real operational constraint for self-hosters.
4. **Filesystem as the API, compiled.** Discovery never imports authored modules ([`packages/eve/src/discover/discover-agent.ts:L84-L106`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/discover/discover-agent.ts#L84-L106)). It writes inspectable artifacts (`agent-discovery-manifest.json`, `diagnostics.json`, `compiled-agent-manifest.json`, `module-map.mjs`) under `.eve/` ([`packages/eve/src/compiler/artifacts.ts:L141-L148`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/compiler/artifacts.ts#L141-L148); [`packages/eve/src/compiler/compile-agent.ts:L79-L88`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/compiler/compile-agent.ts#L79-L88)). Path-derived names mean no `name` fields, and defaults are overridden by writing a file at the same path. The cost is a manifest schema at **v54** ([`packages/eve/src/compiler/manifest.ts:L63`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/src/compiler/manifest.ts#L63)) after four months, plus a build step for every change, mitigated in dev by the watcher.
5. **App runtime vs. sandbox split.** Credentials and integration code stay app-side and only shell work enters the sandbox. This is cleaner than putting the whole agent in a container (OpenHands-style). The flip side is that authored tools are fully trusted, and the default local fallback (just-bash) is an emulator, not an isolation boundary.
6. **Approvals as identity-aware policies.** Request and response policies, approver identity, cross-agent relay, an LLM `auto()` that fails closed, and re-check-before-run are richer than the mode-based approvals in CLI harnesses. It fits multi-tenant backends (Slack threads with several humans) rather than single-user terminals.
7. **Vendoring everything.** One runtime dependency reduces supply-chain exposure and version skew. It also means users cannot independently upgrade `@workflow/*`, `@vercel/sandbox` or the AI SDK providers. Custom Workflow worlds must match eve's vendored protocol line. The docs say `5.0.0-beta` ([`execution-model-and-durability.mdx:L184`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/docs/concepts/execution-model-and-durability.mdx#L184)) while the manifest pins `@workflow/core` `5.2.0` ([`packages/eve/package.json:L624`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/packages/eve/package.json#L624)). **This is a docs/code inconsistency.**
8. **Pre-1.0, breaking changes preferred** ([`AGENTS.md:L137-L138`](https://github.com/vercel/eve/blob/2e45423acff29b02a705a64e6d3b2dff10c1fd4d/AGENTS.md#L137-L138)). Combined with ~1.6 releases per day, it is a moving target. The 1,127 test files, 341 e2e evals, research-doc gating for public APIs and the invariant guard partly offset the churn.

| Dimension | Score (1–5) | Rationale |
|---|---|---|
| Flexibility | 4 | Nearly every layer is swappable through files or interfaces: defaults are same-path slots, and sandbox providers, Workflow worlds, memory providers, channels, models and dynamic resolvers are all replaceable. The harness loop itself is fixed and internal, and hooks are observe-only, so it falls short of 5. |
| Integration | 5 | A full product stack: TUI, web chat, 12 channel families, HTTP API and client SDKs, ACP, MCP server, Vercel Sandbox/OIDC auth, cron, evals, Agent Runs tracing, one-command Vercel deploy. |
| Embeddability | 3 | A typed HTTP client (`eve/client`, React/Vue/Svelte hooks), framework hosts that proxy to an eve server process, and ACP. There is no in-process API to run a session in your own process (§10). |
| Durability | 5 | Workflow SDK durable execution with step replay, delta-encoded checkpoints, crash recovery, parked waits with zero compute, deployment handoff and checkpoint migrations (§6). |
| Safety | 4 | MicroVM sandboxes with domain egress policy and firewall credential brokering (Vercel/microsandbox), secrets kept out of the sandbox, identity-aware request/response approvals, fail-closed ingress auth. Authored tools run unsandboxed, Docker supports only coarse network policy, and the local fallback (just-bash) has no OS isolation. |
| Extensibility | 5 | Namespaced npm extensions, a shadcn-style registry plus skills.sh, hooks, Agent Skills, MCP client and server, OpenAPI connections, dynamic resolvers, custom channels and sandbox providers. Self-modification and the code extension are built on these same APIs. |
| Multi-agent | 4 | Durable, resumable subagent tasks (local, declared, remote) with parallel execution, cross-agent HITL relay, workflow-tool orchestration and a code-mode fan-out of ≤128 agents. No handoff (control transfer) primitive and no worktree isolation. |
| Provider neutrality | 4 | Accepts any AI SDK `LanguageModel` and ships direct Anthropic/OpenAI/Google providers. Defaults lean on Vercel AI Gateway: string ids, cost accounting, catalog context windows, and the `typesafe-ai/jev` decision model for `auto()` and judges. |
| Maturity | 2 | Public beta under Vercel beta terms, `0.79.0` after four months, an explicit prefer-breaking-changes policy and rapid schema churn (manifest v54, checkpoint v15). Heavily tested, and Vercel reportedly runs >100 production agents on it (InfoQ, attributed). |
| Minimalism | 1 | ~276K non-test LOC in the core package. The loop and durability layers alone are ~50K LOC, with many interlocking concepts (owners, anchors, inboxes, tasks, suspended steps, stranded sessions). |

## 14. When to build on it / when not to

**Build on eve when:**
- You are building backend agents that live in Slack/Teams/GitHub/web chat for days or weeks, must survive deploys and crashes, need humans to approve actions (possibly different humans from the requester), and should run shell work in a real sandbox without exposing secrets.
- You want evals, tracing and cron in the same framework, and the "agent as a directory" authoring model, which coding agents handle well (eve benchmarks exactly this).
- You deploy on Vercel, where handoff, Agent Runs, Sandbox egress policy and OIDC all work as designed.

**Think twice when:**
- You self-host and upgrade often. Stranded-session semantics reset conversations on every eve version change on non-Vercel worlds, and you must operate a Workflow world plus a sandbox backend.
- You need very low per-turn latency. Durable checkpoints cost real time on hosted Workflow.
- You want to put the loop inside an existing service. It is a server, not a library.
- You need API stability: it is pre-1.0 and changes weekly.

**Don't use it for:**
- An interactive coding agent with undo/branching, worktrees and editor-native file access (see Codex, OpenCode, Claude Code, Pi).
- A minimal embeddable loop (see pi-agent-core, AI SDK `ToolLoopAgent`, Strands, Pydantic AI).
