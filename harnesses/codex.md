# OpenAI Codex CLI (codex-rs)

> **Verdict.** At the pinned commit, Codex is a very large Rust product (≈1.06 M lines of Rust outside test files (including inline tests) across ~160 crates). It has an extensive safety stack: native OS sandboxes on macOS, Linux and Windows, a Starlark exec-policy engine, a MITM-capable network proxy, and an LLM "Guardian" approval reviewer. Its harness core (`codex-core`) is wrapped by a JSON-RPC **app-server**, and every first-party surface talks to the core through it: the TUI, `codex exec`, the IDE extension, the desktop app and both SDKs. The app-server is therefore the real embedding surface, not the crate API. The loop itself is fixed, the code speaks only the OpenAI **Responses** wire API (Chat Completions was removed), and the Rust crates are unversioned (`0.0.0`) and unpublished. Build on Codex when you want to *drive* a hardened, batteries-included coding agent from your own UI or orchestrator. Don't pick it if you want to reshape the loop, swap providers freely, or embed a small library.

## 1. Layering & package map

The workspace declares about 150 member crates ([`codex-rs/Cargo.toml:L1-L158`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/Cargo.toml#L1-L158)). The important architectural fact at this pin is that **the product surfaces no longer link the agent core directly**. `tui/Cargo.toml` depends on `codex-app-server-client`, `codex-app-server-daemon` and `codex-app-server-protocol`, but not on `codex-core` ([`tui/Cargo.toml:L30-L42`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/tui/Cargo.toml#L30-L42)). ## 2. Agent loop

**Queue pair.** A `Session` is spawned with a bounded submission channel (`SUBMISSION_CHANNEL_CAPACITY = 512`) and an unbounded event channel ([`session/mod.rs:L555-L556`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/mod.rs#L555-L556), [`L647-L648`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/mod.rs#L647-L648)). These are exposed as `SessionIo { tx_sub, rx_event, agent_status, session_loop_termination }` ([`session/mod.rs:L420-L436`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/mod.rs#L420-L436)). A `Submission` carries an `Op`, an optional W3C trace carrier, parent/root turn IDs and a residency guard for multi-agent V2 recipients ([`session/submission.rs:L8-L20`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/submission.rs#L8-L20)). `Op` is `#[non_exhaustive]` and largely in-process: several variants embed `oneshot::Sender` replies, so it is not a serde wire contract ([`protocol.rs:L648-L718`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/protocol.rs#L648-L718)). Events are `Event { id, msg: EventMsg }`, where `EventMsg` is a large tagged union (`TurnStarted`/`task_started`, `AgentMessage`, `ExecCommandBegin/OutputDelta/End`, `ExecApprovalRequest`, `PatchApplyBegin/End`, `TurnDiff`, `PlanUpdate`, `ContextCompacted`, `TokenCount`, …) ([`protocol.rs:L1447-L1639`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/protocol.rs#L1447-L1639)).

**Dispatcher.** `Session::spawn` wraps `spawn_internal` in a `thread_spawn` span and races it against tree shutdown ([`session/mod.rs:L560-L595`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/mod.rs#L560-L595)). It then `tokio::spawn`s `submission_loop` ([`session/mod.rs:L1023-L1047`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/mod.rs#L1023-L1047)). The loop `select!`s, biased, over three sources: agent-tree shutdown, the submission channel, and a multi-agent mailbox watch. It then matches the `Op` variant: `TurnInput`, `RecoverTurn`, `SuspendTurnAndShutdown`, `ThreadSettings`, `TurnSettings`, `InterAgentCommunication`, `ExecApproval`, `PatchApproval`, `UserInputAnswer`, `RequestPermissionsResponse`, `DynamicToolResponse`, `Compact`, `RunUserShellCommand`, `ResolveElicitation`, `Review`, `Shutdown`, plus realtime/voice ops ([`session/handlers.rs:L440-L735`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/handlers.rs#L440-L735)).

**Tasks.** Work runs as a `SessionTask` (`kind`, `run`, `abort`) on its own tokio task with a `CancellationToken` ([`tasks/mod.rs:L172-L221`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/tasks/mod.rs#L172-L221)). `TaskKind` is `Regular | Review | Compact` ([`state/turn.rs:L70-L74`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/state/turn.rs#L70-L74)). `start_task` drains mailbox input into the turn, emits turn-start lifecycle to extensions, admits the turn through the agent execution limiter, and opens a `turn` span with token-usage fields ([`tasks/mod.rs:L288-L383`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/tasks/mod.rs#L288-L383)). `RegularTask::run` emits `TurnStarted` and calls `run_turn` ([`tasks/regular.rs:L31-L70`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/tasks/regular.rs#L31-L70)).

**Turn algorithm.** The loop lives in `run_turn` ([`session/turn.rs:L152-L907`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L152-L907)):

1. Pre-sampling compaction runs **before** the new input is recorded: a model-switch/downshift compaction first, then the token-limit check. On failure the input is still preserved ([`turn.rs:L174-L233`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L174-L233)).
2. Resolve MCP servers and plugins required by `@`-mentions, capture a `StepContext` (settings, tool router, environments), and record context updates ("world state"). Inject skill and plugin items, run `SessionStart` hooks, then run `UserPromptSubmit` hooks and persist the input with `PersistContext::TurnStart` ([`turn.rs:L235-L435`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L235-L435)).
3. Loop. Drain **pending (steered) input** that the user submitted mid-turn and record it with `PersistContext::SteeredUserInput`. Re-capture the step context if new input arrived. Build the prompt from `clone_history().for_prompt(...)` and call `run_sampling_request` ([`turn.rs:L437-L573`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L437-L573)).
4. After sampling, `needs_follow_up = model_needs_follow_up || has_pending_input`. A follow-up turn that crossed the token limit triggers a mid-turn `run_auto_compact` and `continue` ([`turn.rs:L574-L716`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L574-L716)).
5. With no follow-up, `Stop` hooks run. A blocking hook with a continuation prompt injects that prompt and loops again (`stop_hook_active`). The legacy `after_agent` hook and optional post-turn compaction (`model_post_turn_compact_threshold_percent`) run next, then the loop breaks ([`turn.rs:L718-L826`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L718-L826)).
6. Errors: `ContextWindowExceeded` during a Guardian review triggers one compaction retry. `TurnAborted` propagates. Invalid images produce a user-facing error. Everything else emits `EventMsg::Error` and ends the turn so "the user [can] continue the conversation" ([`turn.rs:L829-L904`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L829-L904)).

**Streaming and tool overlap.** `try_run_sampling_request` opens the stream, then processes `ResponseEvent`s ([`turn.rs:L2618-L2714`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L2618-L2714)). Each `OutputItemDone` goes through `handle_output_item_done`. A tool call is persisted immediately and its execution future is pushed into a `FuturesOrdered` **while the stream continues** ([`stream_events_utils.rs:L315-L358`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/stream_events_utils.rs#L315-L358)). Tools therefore start before `response.completed`. `Completed` records token usage; if the server sends `end_turn: false`, it forces a follow-up ([`turn.rs:L3069-L3119`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L3069-L3119)). In-flight tools are then drained under a `codex.tool_blocking` span ([`turn.rs:L3280-L3289`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L3280-L3289)).

**Parallel tool calls.** Requests set `parallel_tool_calls: true` ([`turn.rs:L1666-L1695`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L1666-L1695)). `ToolCallRuntime` gates execution with one `RwLock<()>`: tools that declare `supports_parallel` take a read lock, and all others take the write lock, which serializes them ([`tools/parallel.rs:L141-L220`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/tools/parallel.rs#L141-L220)).

**Steering, interrupts, preemption.** `TurnInputMode` is `StartOrSteer | StartIfIdle | ContinueIfIdle{expected_previous_turn_id} | Steer{expected_turn_id}` ([`protocol/src/turn_input.rs:L192-L202`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/turn_input.rs#L192-L202)). Steered input is queued and folded in before the next sampling request rather than aborting the turn. A `preempt` token can end the current response early. Mail from another agent arriving during a reasoning or commentary item can cut the response short unless `DeferMailboxPreemption` is set ([`turn.rs:L2869-L2932`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L2869-L2932)). `Op::Interrupt` cancels the task; `Op::InterruptIfNoPendingInput` cancels only when nothing is queued.

**Retries.** `run_sampling_request` loops over `handle_response_stream_error` ([`turn.rs:L1707-L1837`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L1707-L1837)). That function:

- records content-filter guidance into history;
- retries connection failures without bound, using exponential backoff (`UnboundedConnectionRetries`, stable and default-on);
- after `stream_max_retries` (default 5, capped at 100), **falls back from WebSockets to HTTPS** and resets the budget;
- honors server `Retry-After` deadlines ([`responses_retry.rs:L57-L164`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/responses_retry.rs#L57-L164), [`model-provider-info/src/lib.rs:L66-L75`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/model-provider-info/src/lib.rs#L66-L75)).

## 3. Model / provider abstraction

**Message model.** Codex uses the Responses API item model directly. `ResponseItem` (`Message`, `Reasoning`, `FunctionCall`, `CustomToolCall`, `LocalShellCall`, `ToolSearchCall`, `WebSearchCall`, `ImageGenerationCall`, `Compaction`, `ContextCompaction`, …) is both the in-memory history and, wrapped in `ResponseItemEnvelope { item, metadata }`, the persisted form ([`history/src/lib.rs:L59-L71`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/history/src/lib.rs#L59-L71)). There is no provider-neutral intermediate representation.

**Provider coverage.** `WireApi` has a single variant, `Responses`. Deserializing `wire_api = "chat"` is a hard error that points users to discussion #7782, and the legacy `ollama-chat` provider ID is likewise rejected ([`model-provider-info/src/lib.rs:L100-L134`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/model-provider-info/src/lib.rs#L100-L134)). Built-in providers are `openai`, `amazon-bedrock`, `amazon-bedrock-runtime` (OpenAI models such as `openai.gpt-5.5` via Bedrock Mantle), `ollama` and `lmstudio`. The source comments that they "do not want to be in the business of adjudicating which third-party providers are bundled" ([`model-provider-info/src/lib.rs:L660-L692`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/model-provider-info/src/lib.rs#L660-L692)). Users add `[model_providers.*]` entries in `config.toml` with these keys: `base_url`, `env_key`, command-backed `auth`, `aws` SigV4, `gateway_oauth`, `http_headers`/`env_http_headers`, `query_params`, retry knobs, `supports_websockets`, and `capabilities` ([`model-provider-info/src/lib.rs:L136-L208`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/model-provider-info/src/lib.rs#L136-L208)). The runtime `ModelProvider` trait exposes `info()`, `capabilities()` and per-provider preferred models for approval review and memory extraction ([`model-provider/src/provider.rs:L102-L140`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/model-provider/src/provider.rs#L102-L140)). Capabilities are upper bounds: `image_generation`, `web_search`, `external_web_access` and `remote_compaction`. `remote_compaction` defaults to `V2` only for OpenAI and Azure Responses providers ([`model-provider/src/capabilities.rs:L30-L53`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/model-provider/src/capabilities.rs#L30-L53), [`model-provider-info/src/capabilities.rs:L10-L28`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/model-provider-info/src/capabilities.rs#L10-L28)).

**Server-driven model metadata.** `ModelInfo` comes from the Codex backend `/models` endpoint, and a bundled `models-manager/models.json` is the fallback. It drives much harness behavior per model:

- `shell_type`, `apply_patch_tool_type` and `web_search_tool_type`;
- `truncation_policy`, `context_window`, and `auto_compact_token_limit` (defaults to 90% of the window);
- `comp_hash` (a compaction-compatibility hash), `supports_search_tool`, `use_responses_lite` and `tool_mode`;
- `model_messages`, which overrides tool descriptions and prompt fragments;
- `guardian` approval coverage.

See [`protocol/src/openai_models.rs:L406-L510`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/openai_models.rs#L406-L510). Much of the "harness configuration" is thus controlled by OpenAI's model catalog rather than by local code.

**Transport and caching.** `ModelClient` is session-scoped. `ModelClientSession` is turn-scoped: it caches a lazily opened Responses **WebSocket**, sticky-routing state (`x-codex-turn-state`), and incremental-request state. Prewarm sends `response.create` with `generate=false` so the next request can reuse the connection and `previous_response_id` ([`client.rs:L1-L26`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/client.rs#L1-L26), [`client.rs:L1109-L1120`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/client.rs#L1109-L1120)). Every request is sent with `store: false`, `stream: true`, `include: ["reasoning.encrypted_content"]` (plus `output.encrypted_content` behind a flag), a `prompt_cache_key`, and `parallel_tool_calls` disabled for Responses-Lite models ([`client.rs:L1040-L1094`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/client.rs#L1040-L1094)). Reasoning state is therefore carried client-side as encrypted blobs replayed in history, which suits zero-data-retention operation. Server-side cache reuse comes from the cache key and the WebSocket incremental path.

**Reasoning controls.** These include `reasoning.effort` (with per-request overrides and `configuration_update` items for models that support them), `reasoning.summary`, `verbosity`, `service_tier`, and a sequential-cutoff summary mode.

**Accounting.** `TokenUsage` tracks input, cached-input, cache-write, output and reasoning tokens ([`protocol.rs:L2366-L2378`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/protocol.rs#L2366-L2378)). It is emitted as `TokenCount` events along with ChatGPT plan `RateLimitSnapshot`s. Codex does **no dollar-cost accounting**: no cost fields were found in `core`, `protocol` or `app-server-protocol`.

## 5. Context management

**Prompt assembly.** Base instructions come from the model catalog (`render_model_instructions`). Older per-model prompt files such as `core/gpt_5_codex_prompt.md` remain in-tree. Layered on top are:

- developer instructions (config, `thread/start.developerInstructions`, managed requirements);
- the collaboration-mode template (`default.md` / `plan.md`);
- permissions instructions;
- AGENTS.md;
- skills, plugin and apps instructions;
- the environment context.

At the pin, all of these model-visible fragments are owned by **"world state" sections**. A `WorldStateSection` has a stable `ID`, a serializable `Snapshot`, and a `render_diff(previous)` that emits only what changed ([`context/world_state/mod.rs:L311-L350`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/context/world_state/mod.rs#L311-L350)). Snapshots are persisted as RFC 7386 merge patches (`RolloutItem::WorldState`) and hashed with SHA-1 ([`world_state/mod.rs:L352-L409`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/context/world_state/mod.rs#L352-L409)). Each update has a `Placement` of `Prefix`, `Standalone` or `Mergeable` ([`world_state/mod.rs:L62-L74`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/context/world_state/mod.rs#L62-L74)). The design appends deltas (for example "cwd changed" or "sandbox changed") instead of rewriting the system prompt, which preserves prefix cache hits. That rationale is an inference from the design, consistent with the "trim from the beginning to preserve cache" comment in `compact.rs`.

**AGENTS.md.** The project root is found by walking up to a `project_root_markers` entry (default `.git`). Every `AGENTS.override.md`, `AGENTS.md` or `project_doc_fallback_filenames` match from that root down to the cwd is concatenated, and the walk never goes past the root ([`agents_md.rs:L1-L18`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/agents_md.rs#L1-L18), [`L272-L296`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/agents_md.rs#L272-L296)). Further rules:

- The budget is `project_doc_max_bytes` (32 KiB default).
- Files are read through each environment's `ExecutorFileSystem`, so remote exec-servers work, under the turn's sandbox when reads are restricted.
- Project docs are **skipped entirely for untrusted projects** ([`agents_md.rs:L58-L116`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/agents_md.rs#L58-L116)).
- User-level instructions come from `$CODEX_HOME/AGENTS.override.md`, falling back to `$CODEX_HOME/AGENTS.md` ([`codex-home/src/instructions/mod.rs:L12-L13`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/codex-home/src/instructions/mod.rs#L12-L13), [`L43-L44`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/codex-home/src/instructions/mod.rs#L43-L44)).

**Compaction.** There are four mechanisms, selected in `run_auto_compact` ([`turn.rs:L1507-L1612`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L1507-L1612)):

1. **Local summarization** (`RemoteCompactionSupport::Unsupported`). The model receives `SUMMARIZATION_PROMPT` ("CONTEXT CHECKPOINT COMPACTION … handoff summary for another LLM"). Replacement history is then built from recent user messages, newest first, within `COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000`, followed by `SUMMARY_PREFIX + summary` ([`compact.rs:L62-L64`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/compact.rs#L62-L64), [`L264-L447`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/compact.rs#L264-L447), [`L702-L819`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/compact.rs#L702-L819), [`prompts/templates/compact/prompt.md:L1-L9`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/prompts/templates/compact/prompt.md#L1-L9)). If the compaction request itself overflows, the oldest item is dropped and the request retried.
2. **Remote compaction V2** (OpenAI/Azure default). The client sends `compaction_trigger` items over the Responses endpoint, and the server returns an opaque compaction item ([`model-provider-info/src/capabilities.rs:L20-L28`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/model-provider-info/src/capabilities.rs#L20-L28)). It can fall back to foreground compaction.
3. **Token-budget reset** (`TokenBudget`, under development). There is no summarization: a fresh context window is installed, and the model gets `new_context_window` / `get_context_remaining` tools ([`compact_token_budget.rs:L16-L27`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/compact_token_budget.rs#L16-L27)).
4. **Async/speculative compaction** (`AsyncCompaction`, under development). A background request is prepared off the hot path and adopted at checkpoints ([`session/async_compaction.rs:L1-L37`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/async_compaction.rs#L1-L37)).

Triggers are pre-turn, mid-turn (follow-up past the limit), post-turn (threshold percent), a model switch whose `comp_hash` changed, and a **model downshift** to a smaller context window, which compacts with the *previous* model ([`turn.rs:L1372-L1498`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn.rs#L1372-L1498)). `PreCompact` and `PostCompact` hooks wrap all of these paths.

**Spill-to-disk.** Hook outputs spill to files (`hooks/src/output_spill.rs`). Tool output is truncated rather than spilled.

**Memory.** This is a two-phase background pipeline that runs at root-session start. Phase 1 extracts `raw_memory` and `rollout_summary` from idle rollouts, in parallel, under SQLite leases, and redacts secrets. Phase 2 runs a single consolidation agent over a git-tracked `~/.codex/memories` workspace ([`memories/README.md:L28-L100`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/memories/README.md#L28-L100)). The read path injects memory developer instructions and parses citations.

## 6. State, sessions & durability

**Rollout format.** Each thread writes JSONL lines of `RolloutLine { timestamp, ordinal?, ..RolloutItem }` ([`history/src/lib.rs:L369-L375`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/history/src/lib.rs#L369-L375)). `RolloutItem` is one of `SessionMeta | ResponseItem | InterAgentCommunication | Compacted | TurnContext | TokenUsageRecord | WorldState | SecurityRiskScore | RetainedContext | EventMsg | RealtimeItem` ([`history/src/lib.rs:L215-L231`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/history/src/lib.rs#L215-L231)). A `CompactedItem` stores the summary, the optional `replacement_history`, window IDs and the `compaction_response_id`, so resume can rebuild post-compaction state without re-summarizing ([`history/src/lib.rs:L290-L302`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/history/src/lib.rs#L290-L302)).

Files are named `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<thread_id>[_<rollout_id>].jsonl` ([`rollout/src/recorder.rs:L1739-L1760`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/rollout/src/recorder.rs#L1739-L1760)). Archived threads live in `archived_sessions/` ([`rollout/src/lib.rs:L85-L95`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/rollout/src/lib.rs#L85-L95)). A fire-and-forget worker compresses cold rollouts to `.zst` ([`rollout/src/compression.rs:L30-L57`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/rollout/src/compression.rs#L30-L57)). `RolloutRecorder` is a background writer task driven by `AddItems | Persist | Flush | Shutdown | Discard` commands. It holds a writer lock and surfaces terminal I/O failures to later calls ([`recorder.rs:L77-L189`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/rollout/src/recorder.rs#L77-L189)). Thread metadata, logs, goals, read-state, guardian feedback and memory jobs live in a SQLite state DB (`sqlx`, 61 migrations under `state/migrations`).

**Pluggable store.** `ThreadStore` is a storage-neutral trait. It covers:

- creating, resuming and resuming with store-prepared state;
- appending, persisting, flushing, shutting down and discarding;
- loading history and the latest model context;
- `prepare_fork`, `revert_thread` and `read_thread`.

Optional operations default to `Unsupported` ([`thread-store/src/store.rs:L128-L298`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/thread-store/src/store.rs#L128-L298)). `PersistContext` defines **durability barriers**. `Standard` and `ThreadPreparation` must be synchronous. `TurnStart`, `SteeredUserInput` and `SubagentSpawn` may be enqueued and fenced at a later flush ([`store.rs:L100-L126`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/thread-store/src/store.rs#L100-L126)). `Session::spawn` accepts `Arc<dyn ThreadStore>` ([`session/mod.rs:L527-L528`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/mod.rs#L527-L528)). `LocalThreadStore` and `in_memory` are the in-tree implementations. The pin commit itself is titled "Support store-owned preparation when resuming threads."

**Resume, fork, revert.** `InitialHistory` is `New | Cleared | Resumed(ResumedHistory) | Forked(Vec<RolloutItem>)` ([`history/src/lib.rs:L388-L393`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/history/src/lib.rs#L388-L393)). Forks can be `Copied`, `CopiedDeferred` or `Referenced { history_base, inherited_item_count }`. A referenced fork points at the parent's prefix instead of copying it ([`session/mod.rs:L444-L453`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/mod.rs#L444-L453)). `ThreadHistoryMode` is `Legacy | Paginated` ([`protocol.rs:L883-L887`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/protocol.rs#L883-L887)). `thread/revert` writes a **new immutable rollout file** that references the retained prefix; the only mutable cutover is the SQLite rollout-path pointer ([`thread-store/src/local/revert_thread.rs:L1-L4`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/thread-store/src/local/revert_thread.rs#L1-L4)). The CLI exposes `resume`, `fork`, `archive`, `unarchive`, `delete`, `queue` and `migrate-rollouts` ([`cli/src/main.rs:L145-L244`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/cli/src/main.rs#L145-L244)).

**Crash and daemon recovery.** `SuspendTurnAndShutdown` behaves as follows ([`session/turn_suspension.rs:L13-L60`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/turn_suspension.rs#L13-L60)):

1. It refuses to act when the task is non-regular or the thread has live descendants.
2. It flushes the rollout before cancelling, "so a persistence failure leaves the original turn running."
3. It records the turn for later `Op::RecoverTurn`.

`interrupted_turn()` captures a regular turn only after its input is recorded, and only for a single local environment whose config is `FromThread`, because "Remote identities/configuration are not persisted across daemon restarts" ([`session/daemon_recovery.rs:L1-L56`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/daemon_recovery.rs#L1-L56)). Recovery re-runs the turn from recorded input; it does not replay individual tool calls. This is turn-granular recovery, not durable execution.

**Undo.** There is no filesystem checkpointing at the pin. `GhostCommit` is marked `Stage::Removed`. `TurnDiffTracker` produces the `TurnDiff` event, and `codex apply` applies a diff.

## 7. Safety & sandboxing

**Two orthogonal axes.** `AskForApproval` is `untrusted` (`UnlessTrusted`), `on-request` (the default; `on-failure` is an alias), `never`, or `granular` with per-category booleans: `sandbox_approval`, `rules`, `skill_approval`, `request_permissions`, `mcp_elicitations` ([`protocol.rs:L1095-L1135`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/protocol.rs#L1095-L1135)). The legacy `SandboxPolicy` is `danger-full-access | read-only{network_access} | external-sandbox{network_access} | workspace-write{writable_roots, network_access, exclude_tmpdir_env_var, exclude_slash_tmp}` ([`protocol.rs:L1177-L1229`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/protocol.rs#L1177-L1229)). It is now compiled into a richer `PermissionProfile::{Managed{file_system, network}, Disabled, External{network}}`, selected by named `[permissions.<id>]` profiles ([`protocol/src/models.rs:L425-L439`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/models.rs#L425-L439)). Writable roots keep `.git`, `.codex` and other protected metadata names read-only ([`protocol.rs:L1231-L1283`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/protocol.rs#L1231-L1283)).

**Matrix for commands not matched by any exec-policy rule** ([`exec_policy.rs:L770-L855`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/exec_policy.rs#L770-L855); the default requirement is at [`tools/sandboxing.rs:L196-L232`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/tools/sandboxing.rs#L196-L232)):

| Approval \ FS sandbox | Restricted (read-only / workspace-write) | Unrestricted / External |
|---|---|---|
| `never` | Allow; the sandbox enforces | Allow |
| `on-request` | Allow sandboxed; prompt only if the model requests escalation (`requests_sandbox_override`) | Allow |
| `granular` | As on-request; a prompt becomes a rejection if that category is `false` | Allow |
| `untrusted` | Prompt | Prompt |
| *Dangerous command, or Windows managed-FS without a sandbox backend* | `never` → **Forbidden**; otherwise Prompt | same |

Exec-policy rules override this matrix. Rules are Starlark `prefix_rule(pattern, decision=allow|prompt|forbidden, justification, match, not_match)` plus `host_executable(name, paths)`, and `match`/`not_match` examples are validated at load time like unit tests ([`execpolicy/README.md:L1-L30`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/execpolicy/README.md#L1-L30), [`execpolicy/src/parser.rs:L347-L440`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/execpolicy/src/parser.rs#L347-L440)). Files live in `rules/*.rules` with `default.rules` as the default ([`exec_policy.rs:L53-L56`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/exec_policy.rs#L53-L56)). Approving with `ApprovedExecpolicyAmendment` persists a new prefix rule ([`handlers.rs:L177-L199`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/handlers.rs#L177-L199)).

**OS sandboxes.** `SandboxType` is `None | MacosSeatbelt | LinuxSeccomp | WindowsRestrictedToken | WindowsMxc` ([`protocol/src/sandbox.rs:L28-L35`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/sandbox.rs#L28-L35)). The choice is per platform ([`sandboxing/src/manager.rs:L50-L64`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/sandboxing/src/manager.rs#L50-L64)), and only when the profile requires one ([`manager.rs:L313-L353`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/sandboxing/src/manager.rs#L313-L353)).

- **macOS.** Uses `/usr/bin/sandbox-exec` only, never a binary found on `PATH`, with `.sbpl` profiles compiled in via `include_str!` ([`seatbelt.rs:L21-L62`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/sandboxing/src/seatbelt.rs#L21-L62)). The base profile is `(deny default)`, "inspired by Chrome's sandbox policy" ([`seatbelt_base_policy.sbpl:L1-L12`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/sandboxing/src/seatbelt_base_policy.sbpl#L1-L12)).
- **Linux.** `codex-linux-sandbox` applies `no_new_privs` and seccomp in-process, with **bubblewrap** providing filesystem isolation ([`linux-sandbox/src/lib.rs:L1-L5`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/linux-sandbox/src/lib.rs#L1-L5)). The bwrap binary is bundled and digest-verified, and its source is vendored at `codex-rs/vendor/bubblewrap`. The old Landlock filesystem path is retained, but the helper rejects it for filesystem-restricted policies ([`linux-sandbox/src/seccomp.rs:L1-L5`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/linux-sandbox/src/seccomp.rs#L1-L5)). Focus notes that describe "Landlock+seccomp" are therefore out of date for the default path.
- **Windows.** `windows-sandbox-rs` (24 k LOC) uses restricted tokens, ACL grants and deny-read walkers, dedicated sandbox identities (`elevated/`, `setup_provisioning/`), WFP firewall rules (`wfp.rs`) and ConPTY. A newer `WindowsMxc` backend probes OS "process security environment" support (`sandboxing/src/windows_mxc.rs`, `mxc-sandbox`).

**Network.** `codex-network-proxy` runs a local HTTP proxy (`:3128`) and a SOCKS5 proxy (`:8081`) with allow/deny policy and a `limited` read-only mode. In that mode it does HTTPS MITM with a managed CA whose private key stays in memory, and it blocks hostnames that resolve to private IPs ([`network-proxy/README.md:L1-L50`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/network-proxy/README.md#L1-L50)). Network denials can become approval prompts, and the resulting `NetworkPolicyAmendment`s are persisted.

**Guardian.** `approvals_reviewer = "auto_review"` routes approval requests to an isolated LLM reviewer instead of the user ([`config_types.rs:L183-L190`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/config_types.rs#L183-L190), [`guardian/mod.rs:L1-L3`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/guardian/mod.rs#L1-L3)). The reviewer follows a risk-taxonomy policy prompt covering data exfiltration and trusted destinations (`prompts/templates/guardian/policy.md`), with a denial circuit breaker. A model can also declare `guardian` coverage in its catalog entry.

**Secrets and process.** These are the weakest defaults. `ShellEnvironmentPolicy` inherits **all** environment variables, and `ignore_default_excludes` defaults to `true`, so `*KEY*`/`*SECRET*`/`*TOKEN*` variables reach model-run commands unless the user configures filtering ([`config_types.rs:L233-L245`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/config_types.rs#L233-L245), [`config/src/shell_environment_policy.rs:L136`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/config/src/shell_environment_policy.rs#L136)). `process-hardening` runs pre-`main` in helper binaries such as `responses-api-proxy` and `linux-sandbox`'s proxy. It disables core dumps and ptrace and strips `LD_PRELOAD`/`DYLD_*` ([`process-hardening/src/lib.rs:L7-L14`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/process-hardening/src/lib.rs#L7-L14)). `secrets` provides a keyring-backed store and a `redact_secrets` sanitizer. Enterprise `requirements.toml` (local or cloud-delivered) can pin approval and sandbox settings, login methods and residency.

## 8. Extensibility

**Hooks.** The hook events are `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `SubagentStart`, `SubagentStop`, `Stop` and `Interrupt`. Handler types are `command`, `mcp_tool`, `prompt` and `agent` ([`protocol.rs:L1691-L1713`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/protocol/src/protocol.rs#L1691-L1713)). Hooks load from `hooks.json` next to each config layer or from `[hooks]` tables in `config.toml` ([`hooks/src/engine/discovery.rs:L339-L345`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/hooks/src/engine/discovery.rs#L339-L345), [`L385-L388`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/hooks/src/engine/discovery.rs#L385-L388)). The event names are deliberately **Claude-Code-compatible**. `apply_patch` accepts `Write`/`Edit` matcher aliases, `spawn_agent` accepts `Agent`, and shell tools surface as `Bash` ([`tools/hook_names.rs:L30-L58`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/tools/hook_names.rs#L30-L58), [`hook_runtime.rs:L233-L244`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/hook_runtime.rs#L233-L244)). A `Stop` hook can block and inject a continuation prompt (§2). Hooks are a stable feature, enabled by default.

**Skills.** Skills are `SKILL.md` directories. Roots are scanned in this order ([`ext/skills/src/host_roots.rs:L24-L110`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/ext/skills/src/host_roots.rs#L24-L110)):

1. `<project config folder>/skills`;
2. `$CODEX_HOME/skills` (deprecated);
3. `~/.agents/skills`;
4. plugin skill roots;
5. repo `.agents/skills` up the ancestor chain.

The bundled `.system` skills are `imagegen`, `openai-docs`, `review-agent`, `skill-creator` and `skill-installer` ([`skills/src/lib.rs:L58-L61`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/skills/src/lib.rs#L58-L61)). The skills extension renders a catalog prompt under a `skill_max_context_tokens` budget and supports `$skill` mentions, cloud skills and a `SkillSearch` dynamic selector.

**Plugins.** Plugins bundle skills, MCP servers, hooks and apps. Manifests are discovered at `.codex-plugin/plugin.json`, **`.claude-plugin/plugin.json` and `.cursor-plugin/plugin.json`** ([`exec-server-protocol/src/protocol.rs:L51-L55`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/exec-server-protocol/src/protocol.rs#L51-L55)). Marketplaces are read from `.agents/plugins/marketplace.json`, `.claude-plugin/marketplace.json` and `.cursor-plugin/marketplace.json` ([`core-plugins/src/marketplace.rs:L20-L25`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core-plugins/src/marketplace.rs#L20-L25)). The CLI has `codex plugin` subcommands, and the app-server exposes `plugin/*` and `marketplace/*` methods. `external-agent-migration` imports config, skills, AGENTS.md, plugins, MCP config, subagents, hooks, commands and sessions from Claude Code (`Cla`) and Cursor (`Cur`) ([`migration_source.rs:L52-L56`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/external-agent-migration/src/migration_source.rs#L52-L56), [`model.rs:L53-L61`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/external-agent-migration/src/model.rs#L53-L61)).

**MCP client.** `codex-mcp` and `rmcp-client` are built on the official `rmcp` Rust SDK, pinned at 3.5.1 ([`codex-rs/Cargo.toml:L451`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/Cargo.toml#L451)). Transports are `stdio` and `streamable_http` with bearer-env or OAuth (`codex mcp login`) ([`config/src/mcp_types.rs:L612-L640`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/config/src/mcp_types.rs#L612-L640)). Per-tool approval is `auto | prompt | writes | approve` ([`mcp_types.rs:L26-L33`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/config/src/mcp_types.rs#L26-L33)). Elicitations and resources are supported, and tools can be deferred behind `tool_search`.

**MCP server: removed.** `codex mcp-server` and the `codex-mcp-server` crate were deleted by PR #42993 on 2026-09-05. That PR body says it removes "the standalone `codex-mcp-server` crate, including its tests, interface documentation…". This matches OpenAI's blog account that "exposing Codex as an MCP server" was tried first and abandoned in favor of the app-server.

**In-process extension API.** `ext/extension-api` defines contributor traits: `ContextContributor`, `ThreadLifecycleContributor`, `TurnLifecycleContributor`, `TurnInputContributor`, `ToolContributor`, `ToolLifecycleContributor`, `ApprovalReviewContributor`, `TurnItemContributor`, `McpServerContributor`, `TokenUsageContributor`, `ModelRequestContributor` and `ModelResponseInterceptor` ([`contributors.rs:L84-L428`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/ext/extension-api/src/contributors.rs#L84-L428)). It is a **compile-time** Rust seam: the app-server hard-codes which extensions are installed (queue, history-notes, message board, goal, git-attribution, guardian-v2, memories, MCP, web-search, image-generation, skills) ([`app-server/src/extensions.rs:L50-L122`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/app-server/src/extensions.rs#L50-L122)). Third parties can't load extensions at runtime.

**Configuration.** There are 176 feature flags with `UnderDevelopment | Experimental | Stable | Deprecated | Removed` stages ([`features/src/lib.rs:L48-L63`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/features/src/lib.rs#L48-L63)). Configuration also covers profiles, layered `config.toml` (system, user, project, cloud) and custom prompts and slash commands.

## 9. Multi-agent

Collaboration tools are enabled per `MultiAgentVersion` ([`spec_plan.rs:L724-L741`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/tools/spec_plan.rs#L724-L741)):

- **V1** (`Collab`, stable, default-on) offers `spawn_agent`, `send_input`, `resume_agent`, `wait_agent` and `close_agent`. These are deferred behind `tool_search` when the model supports it.
- **V2** (`MultiAgentV2`, stable, default-off) offers `spawn_agent{message, task_name, agent_type?, model?, reasoning_effort?, fork_turns: "none"|"all"}`, `send_message`, `followup_task`, `wait_agent`, `interrupt_agent` and `list_agents` ([`multi_agents_v2/spawn.rs:L201-L240`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs#L201-L240)).

Children are full `Session`s with their own rollouts, sharing the `ThreadManager`. Limits are `agent_max_threads = 6` and `agent_max_depth = 1` by default ([`core/src/config/mod.rs:L255-L265`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/config/mod.rs#L255-L265)), enforced via `AgentLimitReached` ([`agent/registry.rs:L85-L98`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/agent/registry.rs#L85-L98)). Communication is a **mailbox**. `Op::InterAgentCommunication` enqueues messages, and `trigger_turn` can wake an idle agent ([`handlers.rs:L80-L97`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/src/session/handlers.rs#L80-L97)). Mail can preempt an in-flight response (§2). Other pieces:

- `agent-roles` loads role definitions (`agent_type`).
- `agent-graph-store` persists the parent/child graph.
- `ext/agent-message-board` provides shared discussion boards.
- **Goals** (`/goal`, stable, default-on) re-start turns on idle via `on_thread_idle → continue_if_idle` until the goal completes or its token budget runs out ([`ext/goal/src/extension.rs:L180-L203`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/ext/goal/src/extension.rs#L180-L203)).

**Worktrees.** `codex-worktree` creates Desktop-compatible managed git worktrees ([`worktree/src/lib.rs:L26-L50`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/worktree/src/lib.rs#L26-L50)). It is used by `codex exec --worktree` and the TUI agents overview. Subagents do **not** get worktree isolation: they share their parent's environments unless the host supplies isolation.

**Review.** `Op::Review` spawns a review sub-thread, and `codex review` is the headless form.

**Reuse analysis.** These are the options from cheapest to most invasive:

- **Drive Codex from another program.** The app-server over stdio is the supported contract, used by the IDE, the desktop app, the Python SDK, Hermes, OpenClaw and the AI SDK harness adapter. You get approvals as server requests, dynamic tools, `developerInstructions`/`baseInstructions` overrides, per-thread sandbox and permission profiles, and history pagination.
- **Embed in Rust.** `codex_app_server::in_process` keeps the same semantics without a process boundary. Calling `codex-core`'s `ThreadManager` directly is possible but means pulling in ~1 M lines of unpublished `0.0.0` crates with no API stability promise ([`core/Cargo.toml:L1-L5`](https://github.com/openai/codex/blob/b7ba02f88095cd3c039709157618c03909d47a26/codex-rs/core/Cargo.toml#L1-L5)).
- **Customize without forking.** Available levers are config/profiles, AGENTS.md, skills, hooks, MCP, plugins, dynamic tools, custom Responses-compatible providers, and a custom `ThreadStore` (Rust only).
- **Change the loop, tool router, compaction, or wire API.** These require a fork.

## 12. Notable design decisions & trade-offs

1. **The app-server became the harness API, and MCP-server mode was deleted.** Every first-party UI, including the TUI, now goes through the same JSON-RPC `MessageProcessor`, sometimes in-process. That gives one execution contract and one schema across surfaces, at the cost of a 175-method protocol that is far broader than an "agent API". Embedders inherit product concepts such as projects, sections, read-state, remote control and attestation.
2. **Responses-only, stateless with encrypted reasoning.** Dropping Chat Completions (`wire_api = "chat"` is a hard error) lets the harness use Responses-specific features: encrypted reasoning replay with `store:false`, WebSocket incremental requests with `previous_response_id`, freeform grammar tools, hosted web search, remote compaction V2 and `end_turn`. It narrows provider neutrality to Responses-compatible endpoints: OpenAI, Azure, Bedrock-Mantle, Ollama and LM Studio.
3. **Server-driven behavior.** `ModelInfo` from the backend selects the shell tool type, patch tool, truncation, compaction threshold, tool mode, prompt and tool descriptions, and Guardian coverage. Behavior can change without a client release, but reproducing a given run requires the catalog snapshot (`codex debug models`).
4. **Context as diffed world state.** Model-visible environment state is a set of typed sections that emit deltas and persist merge patches. This is more machinery than a re-rendered system prompt, but it keeps the prompt prefix stable for caching and makes resume deterministic.
5. **Tools start during streaming; a reader/writer lock gives conservative parallelism.** Overlapping tool execution with the stream reduces latency. A single global `RwLock` serializes every non-parallel tool against all others.
6. **Approval and sandbox are orthogonal, and denial-escalation is centralized.** `ToolOrchestrator` is a reusable pattern: approve once, run sandboxed, retry unsandboxed on denial without re-prompting. The matrix still has sharp edges, notably Windows without a sandbox backend and the inherit-all environment default.
7. **Durability is turn-granular.** JSONL plus SQLite plus explicit `PersistContext` barriers and daemon turn recovery is strong for an interactive tool. It is still not durable execution: tool side effects are not journaled or replayed, and there is no filesystem undo now that GhostCommit is removed.
8. **Compatibility with Claude Code as a strategy.** Hook names and matcher aliases, `.claude-plugin` manifests and marketplaces, and a migration importer for Claude and Cursor configs and sessions all lower switching costs. This is visible in code, not just in documentation.
9. **Scale and churn.** 176 feature flags, two multi-agent versions, four compaction strategies and legacy/paginated history modes coexist. Stale docs (`protocol_v1.md`) and focus-note assumptions (`codex.rs`, `mcp-server`, Landlock) are already wrong at this pin, so readers should trust the code over prose.

## 14. When to build on it / when not to

**Build on Codex when:**

- You want a production-grade coding agent with OS sandboxing and approval machinery across three desktop platforms, and you are happy to drive it as a black box over the app-server protocol, as the IDE extension, Hermes, OpenClaw and the AI SDK's `@ai-sdk/harness-codex` do.
- You target OpenAI models (or Responses-compatible endpoints) and want encrypted-reasoning, WebSocket incremental requests, remote compaction and hosted web search handled for you.
- You need Claude-Code-compatible hooks, skills and plugins on a different agent, or a migration path off Claude Code or Cursor.
- You want headless CI or batch runs (`codex exec --json`, `--output-schema`) with resumable sessions.

**Don't build on it when:**

- You need a small, readable, in-process library whose loop you can rewrite. Prefer pi-agent-core, Flue, Strands or the OpenAI Agents SDK.
- You need first-class non-OpenAI providers (Anthropic, Gemini, Chat Completions-only gateways); prefer OpenCode, Goose or the Vercel AI SDK.
- You need durable, step-level execution with replay; prefer the workflow-backed frameworks.
- You need ACP or an MCP-server interface natively. Neither exists in-tree; use the third-party `codex-acp`.
